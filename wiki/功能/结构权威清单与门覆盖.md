# 结构权威清单与门覆盖

## 一、用户获得什么

**裁定：介于产品 API 与纯实现细节之间——它是产品必须提供的机器可读治理接口，但不是终端用户编程接口。**

用户真正获得的承诺是：所有能把受治理输入带到持久副作用的 public ingress，都经过同源 gate；新增入口、sink 或豁免不能静默绕开。canonical ingress/sink/gate manifest 是证明这项承诺所必需的产品侧 SSOT。

承诺对象：

1. runtime 维护者：登记产品有意开放的 ingress、durable sink 与 gate。
2. 验证种系和 CI/release gate：机器消费目录，做覆盖、dominance、ratchet 与豁免审计。
3. 独立发布审计者：从发布来源与证据包复核“本版本声明了什么、还欠什么”。

终端用户不需要编辑、配置或理解该清单；产品也不承诺内部函数名、模块布局或 ingress/sink 数量永不变化。

### 清单承诺

1. **单一权威**：产品仓只有一个 canonical manifest；测试、文档和 gate 不手抄第二份 ingress/sink/gate 目录。
2. **机器可发现**：manifest 有稳定发现方式、`schema_version`、产品版本/source revision，并能无歧义标识每个 ingress、sink、gate。
3. **A/B/C 诚实分类**：
   - A：已纳入结构证明。
   - B：显式缺口，必须有 owner、原因与退出计划；存在 B 时不得声称结构 authority 全绿。
   - C：闭集豁免，必须有 category、reason、owner 及证明无法接受/生成未验证值的方向 canary。
4. **新增即 ratchet**：新 public ingress、durable sink、gate 或相关 cfg target 未登记时 fail loud，不能靠 generic scanner 或默认忽略通过。
5. **三因子不互代**：manifest 只提供“申报”；调用图 dominance 证明“结构上必经”；fresh/existing/late-mutation 等行为反证证明“运行时不旁路”。三者缺一不得签完整 authority。
6. **产品与验证分工**：产品维护 manifest 和真实结构；验证侧只消费、对账和给 verdict，不能为方便测试自行发明目录。

### 稳定性与破坏性变更纪律

- 稳定承诺：manifest 的发现方式、schema 版本协商、A/B/C 语义、必填审计字段和 fail-loud 原则。
- 非稳定承诺：具体内部 symbol、条目数量、模块路径和调用图形状；这些可随实现改变。
- 任一条目新增、删除、改类、改 symbol 或改 gate/sink 关系，必须与产品改动同片更新 manifest，并重新跑结构与行为证明。
- schema 字段或语义不兼容时必须提升 `schema_version`，同步更新生成器/消费者/迁移说明；未知 schema 必须拒绝，禁止猜读。
- 内部条目变化若不改变用户行为，不自动构成产品 semver breaking；但属于 release-governance breaking change，必须在结构审计 diff 中显式出现。

## 二、怎样黑盒判真

1. 从稳定发现位置读取 manifest；缺文件、未知 schema、source revision 不匹配均专属失败。
2. 从产品公开入口发现面与 durable-effect 边界反查实际集合；未登记入口/sink 分别报 `UNREGISTERED_PUBLIC_INGRESS` / `UNREGISTERED_DURABLE_SINK`。
3. 每个 symbol 必须解析唯一；零命中、多命中、cfg-only 未覆盖均 fail loud 或进入带 owner/plan 的 B/C。
4. 对 A 项构造 interprocedural 调用/控制流图；每条 ingress→sink 路径必须经过 gate 成功返回，错误返回不算验证。
5. B 缺 owner/plan、C 缺 category/reason/owner/canary 均失败。
6. synthetic 新 ingress、新 sink、动态未知调用、跨 target 项分别触发专属 ratchet 红，证明 manifest 不是静态装饰。
7. 同轮运行行为反证：fresh/existing workspace、late observation/mutation 和合法输入正控；结构绿不能替代行为绿。
8. 测试从 manifest 枚举，不手抄当前 I/S/G 表；对 manifest 添加 canary 条目时，所有相关消费者必须共同看见。

## 三、现在处于什么状态

**0.5.60 已发布时点：未实现；0.5.61+ 待立项。**

`.team/artifacts/germline-increments/0.5.61-structural-authority-harness-signoff.md` 已独立证实：

- rustdoc JSON 可枚举当前 public Rust API；
- MIR 可观察当前调用序，但 stable MIR 只有不保证 schema 的文本；
- 仓内没有 canonical ingress/sink/gate manifest；
- 验证侧若自行解析 textual MIR 或手抄当前 I01–I09/S01–S09，只会制造第五个弱 scanner/第二份漂移目录。

因此 T01a 结构面保持 BLOCKING；在 manifest 与结构化调用图工具分别补齐前，只能诚实标长期待补认，不能用更多文本扫描绕过。

## 四、边界与非目标

1. manifest 不是用户可配置 workflow、role DSL 或权限策略。
2. 不把具体内部 symbol 提升为长期公共 API。
3. 不承诺 rustc textual MIR schema，也不要求产品为测试稳定第三方编译器内部文本。
4. manifest 本身不能证明 dominance；compiler-backed graph/extractor 是独立工具面。
5. 不因有 manifest 就免除行为黑盒、正控、跨平台/cfg 证据。
6. 不允许验证侧把 exact-tip 观察表复制成“canonical”文件后反向要求产品服从。
