# F9：显示、平台、安装与黑盒体验

## 一、用户获得什么

用户完成一次安装后，可以在日常 CLI 对话中开团、观察成员和取得结果；不需要理解内部 runtime、tmux socket、状态文件或命令链。成员界面可见、可操作、可滚动；平台差异由基础设施吸收，清理只触碰团队拥有的资源。

用户可见承诺：

1. **开箱即用**：安装、自升级、版本核对和启动入口短且可诊断。
2. **黑盒体验**：普通用户不读源码、不手编运行 manifest、不操作底层 tmux。
3. **显示可选且不夺权**：headless 与可见窗口都能工作；显示层只观察/操作既有能力，不成为唯一控制面。
4. **跨平台语义一致**：macOS、Linux、WSL/Windows 的入口与结果语义一致；平台不支持时明确标 preview/unsupported。
5. **资源边界精确**：停止、升级、清理不误杀用户终端、sibling team 或别的 socket/session。
6. **失败三件套**：错误给出简短原因、可执行动作和日志位置，不把 stack trace/源码路径塞给用户。
7. **cursor 订阅启动的代理键（在途，锚 `10137cda`，未发版）**：起 cursor 席需要代理（派单给定实测）。订阅路径的 worker 环境必须透传代理键。代理值内含凭据：本页、日志、报告、status/diagnose 输出都只写有无，不许出现值。
8. **Pi 安装与黑盒入口（用户会签 2026-08-31）**：npm、Homebrew、WSL 等标准安装形成的 Pi 可执行文件或符号链接均应可用。可执行文件解析遵循 shell 的 PATH-first 语义。不得越过 PATH 中首个可执行 `pi` 选择后置私有 wrapper，也不得要求用户额外提供 Team Agent 专属的 verified wrapper。Pi 既可从普通可寻址 tmux pane 启动，也可通过 Team Agent 团队生命周期启动；用户无需理解或操作底层 tmux socket。“支持普通 tmux pane”不等于要求用户管理 tmux。`team-agent pi` 省略 model/effort 时可以启动，见 [[F3 Provider、模型、权限与资源组合]]。条款地图 [[Pi provider 适配]]。

明确非目标（Pi，用户会签 2026-08-31）：

- 扫描完整 PATH 并绕过首个 `pi`。
- 要求 Team Agent 专属 wrapper 身份。
- 把 tmux 内部操作变成普通用户必须学习的产品流程。

准则锚：

- `docs/team-agent-foundation-and-boundaries.md` §5、§16、§18、§20–§21
- `docs/team-agent-codex-foundation-rust-goal.md` §1、§5、§9、§12

## 二、怎样黑盒判真

### 安装与一键入口

原文锚：quick-start goal §1、§9、§12；基础边界 §18。

1. 在干净环境安装已发布包，不从源码运行。
2. 只提供用户可读团队/角色文档，一次入口到 ready。
3. 升级后版本、daemon 与 worker 使用同一已发布 runtime；旧 daemon 不得静默继续服务。
4. 失败输出只含原因、动作、日志，且不泄露 secret。
5. 订阅路径启动 cursor 席时，worker 环境中代理键存在（只核键名有无）；对运行状态、诊断、事件、失败输出与本页做全文检查，代理值不得出现。（在途，锚 `10137cda`，未发版）
6. npm、Homebrew、WSL 等标准安装形成的 Pi 可执行文件或符号链接均应可用；解析遵循 PATH-first；不得越过 PATH 中首个可执行 `pi` 选择后置私有 wrapper；也不得要求 Team Agent 专属 verified wrapper。（用户会签 2026-08-31）
7. Pi 既可从普通可寻址 tmux pane 启动，也可通过 Team Agent 团队生命周期启动；用户无需理解或操作底层 tmux socket；不得把 tmux 内部操作变成普通用户必须学习的产品流程。（用户会签 2026-08-31）

### 可见可操作显示

原文锚：基础边界 §16；Codex foundation goal §9 第 2–3、9 条。

1. headless 模式下完整消息/结果链可用。
2. 选择可见显示后，每个 worker 可查看、滚动和输入，不要求学习 tmux 快捷键。
3. 关闭显示 client 不等于杀 team；team shutdown 也不误杀用户终端。
4. 显示失败只降级显示能力，不丢消息、会话或状态。

### 跨平台与资源隔离

原文锚：基础边界 §6、§7、§16；各 goal 的真实验收与失败必须 partial/blocked 规则。

1. macOS、Linux、WSL/Windows 分别跑安装→开团→收发→结果→停止→恢复→清理。
2. 每个平台用真实 transport；编译通过不能替代真实运行。
3. 同机两个 team 与用户自有终端并存，停止其中一个后其余保持可用。
4. 临时 HOME、registry、socket 与测试资源全部回收，真实用户目录零污染。

## 三、现在处于什么状态

**0.5.57 时点：部分。**

已实现：

- npm 已发布安装/升级入口、黑盒 skill、一键开团、headless 与 Ghostty/tmux 显示后端。
- macOS/Linux 主路径与 0.5.57 自升级、订阅场景、停止/恢复门已有发布证据。
- 私有 tmux socket、精确 teardown、资源归属与隔离门已形成。

仍未完整：

- Windows-native/ConPTY 历史验收仍有部分项和真实订阅 provider 登录缺口；preview 不能算跨平台完整实现。
- 显示体验的“用户不学 tmux、每个 worker 原生可操作”并非所有终端/backend 均有同等证据。
- `.team/TASKS.md` §4.11 记录自升级误杀在跑长任务，说明升级前资源清点与长任务保护仍有缺口。

发布证据：`.team/TASKS.md` §4.11「0.5.57 发版闭环」的 npm latest、自升级、订阅三场景和库存升级门；`origin/main` CHANGELOG 连续版本记录作为已发布真相源之一。

1. 基础边界 §6 长期要求 leader 不被 tmux 绑定，后续又有 managed launcher；两种合法拓扑的默认选择与长期地位需用户会签。

3. 早期 goal 把 Windows/Claude 等列为当轮 out of scope；这是阶段边界，不得覆盖长期跨平台/跨 provider 承诺。
