# F6：任务、结果与交付闭环

## 一、用户获得什么

leader 可以把一项有边界的工作交给明确成员；成员完成后提交结构化结果。系统保持任务、当前工作轮次和结果的正确归属，并确保真正面向用户的结果进入 leader 主屏，而不是只停在后台存储。

用户可见承诺：

1. **任务归属明确**：一项任务有唯一负责成员；普通消息、ACK 或状态更新不能改写 assignee 或冒充完成。
2. **结果结构可验证**：结果至少表达状态、摘要、变更、验证、风险、产物和下一步；非法结构在污染任务状态前被拒绝。
3. **结果归属当前轮次**：成员的新结果优先归属于当前正在处理的消息/任务，不能回填到旧任务或已完成轮次。
4. **同一结果只交付一次**：重复报告、恢复或 watcher 重跑不能给用户制造第二份结果。
5. **持久化不等于用户交付**：结果落库只证明可追踪；用户交付只有进入 leader 主屏后才清偿。
6. **流水线结果可归档**：普通结果默认用户可见；只有 task 由派单方显式声明 `result_route=pipeline` 时才进入 casefile/durable-only，状态事实失败仍无条件穿透。
7. **证据与结论一致**：声称通过时，验证字段必须含真实执行证据；未执行、失败或结构不被识别时必须诚实标明。
8. **结果路由由派单方预声明**：task 可声明 `result_route: leader | pipeline`，默认 `leader` 保持零迁移；只有派单方写路由，worker 的 exactly-once 与 durable 契约不变且无需感知去向。
9. **status 只运输不解释**：结果携带的 status 是编排方可自由定义的不透明字符串；框架不得维护词表、解释业务语义、计算轮次或据此改写结论。

## 二、怎样黑盒判真

### 派单与当前轮次归属

原文锚：

- `docs/team-agent-skill-hardening-goal.md` §4「ACK/status 不得污染 task routing」
- 同文 §5 Codex-to-Codex smoke：消息投递到正确 worker，worker 返回合法结果，collect 后对应 task 完成
- `docs/team-agent-quick-start-and-blackbox-goal.md` §9：worker 完成后调用 `report_result`，结果自然进入 leader

黑盒验收：

1. 先给成员任务 A，再发一条不应产生结果的普通消息 B，最后给任务 C。
2. ACK/status 不改变 A/C 的 assignee 或状态。
3. C 的结果只能归属于 C；不能回填 A，也不能把 B 误识别为 reportable task。
4. 同一成员并行存在多个候选历史轮次时，无法唯一归属必须明确警告或拒绝。

### 结果结构与原子接收

原文锚：

- `docs/team-agent-skill-hardening-goal.md` §4「result envelope 强校验」：summary 为字符串，changes/tests/risks/artifacts/next_actions 为结构化列表
- 同文「collect 不得部分污染 state」：非法结果不能先改 task status 再崩溃
- 同文 §8：P0 必须有测试，不得仅 documented-only

黑盒验收：

1. 分别提交合法结果、错误字段名、错误标量类型、列表中字符串、缺关键字段五种输入。
2. 只有合法结果被接收；非法结果返回精确字段路径与原因。
3. 拒绝前后任务 assignee/status、既有结果和用户可见呈现均不变。
4. renderer/status 面对坏历史行也不能崩溃或生成伪完成。

### 验证证据诚实性

原文锚：

- 各 goal 的完成标准：任一条件未满足不得声明完成，必须标 blocked/partial 并给证据
- `docs/team-agent-skill-hardening-goal.md` §5：自动化、fake/tmux 与真实 smoke 证据分别列明

黑盒验收：

1. 提交四种 tests：真实执行通过、真实执行失败、明确未运行、结构未知但携带退出码。
2. 系统不得把未运行或未知结构自动归一化为“已验证通过”。
3. 真实执行证据也不能因字段解析缺口被静默改成未运行；若不支持该 schema，应在接收时明确拒绝并给唯一合法形态。
4. leader 最终看到的“通过/部分/阻塞”必须与持久证据一致。

### 用户交付与流水线归档

原文锚：

- `docs/team-agent-foundation-and-boundaries.md` §13：主屏只接收业务消息和确需判断的异常摘要
- `.team/artifacts/0.5.60-message-plane-requirements-20260725.md` §1、§2：默认 leader 零迁移；pipeline route 可归档；状态事实失败无条件穿透
- `docs/team-agent-quick-start-and-blackbox-goal.md` §9：leader 不轮询即可自然收到 worker 结果

黑盒验收：

1. 提交默认 route 结果、pipeline route 结果、failed/fallback 结果和 malformed route 各一次。
2. 默认结果上屏；pipeline 结果按 case 持久化且可拉取；failed/fallback 强制上屏；malformed route 在污染任务前 fail closed。
3. 不允许解析 summary 或 status 文案来猜 route。
4. 同一 result_id 经重复 collect/recovery 后，leader 主屏最多出现一次。

### `result_route` 与流水线结果

正式需求锚：`.team/artifacts/0.5.60-message-plane-requirements-20260725.md` §1「report_result 路由随 task 外部设置」、§2「stage_* 流程语义平面搬家」「框架面最小化重申」。

专项需求与锚号：[[result_route 与流水线结果消费]]。

关联验收：[[communication_mode 黑盒验收矩阵]]。

设计依据：

1. **参数落在信息所在的地方**：结果去向在派单时已经齐备，所以 `result_route` 写在 task 上，由派单方唯一维护，worker 零感知。
2. **任务 outcome 不等于 message-class**：status/outcome 是每个任务自己的契约字段，由派单方定义词表、脚本消费；message-class 是要求发送者揣摩全局分类并让 policy 在运行时改路由。前者是有界任务输入，后者是应当取消的全局分类作业。
3. **worker 报事实、脚本持状态**：worker 只报 status、失败签名和报告引用；轮次、阈值、分支表与词表说明由确定性脚本维护并组装进派单提示词。
4. **预声明消化可预见异常**：已写入脚本的换轨条件属于计划内分支；只有真正计划外的 failed/fallback 才穿透 leader。
5. **分界自检**：“这是不是编排脚本的内容？”若是，就不进入框架需求。死结根因分类、诊断站选择和新增站型属于编排层素材；框架只运输事实与 route，不解释根因、不替 leader 改编排。

推导背景详见：

- `/Volumes/nvme/Projects/讨论team-agent/wiki/patterns/确定性编排平面.md`
- `/Volumes/nvme/Projects/讨论team-agent/wiki/techniques/开发分身工作协议.md`
- `/Volumes/nvme/Projects/讨论team-agent/wiki/architectures/以开发为中心的拓扑.md`

黑盒验收：

1. task 未声明 `result_route` 时等价于 `leader`：既有 worker 无需迁移，结果按原路径进入 leader。
2. task 声明 `pipeline` 时，结果持久落 result store，由编排脚本消费触发下一站；leader 侧只形成可回溯 casefile 归档，不即时上桌。
3. `result_route` 的唯一写者是派单方；worker 不能在结果中覆盖、补写或猜测路由。
4. failed/fallback 等计划外失败无条件穿透到 leader，不受 `pipeline` 声明约束。
5. 两种 route 都保持同一 durable、result_id、exactly-once 与任务归属；路由不得生成第二份结果。
6. status 原样运输给编排脚本；使用未知、自定义或新 status 时框架不得拒绝、归一化、翻译或分支。
7. 阈值、轮次、分支表、预期异常和下一站全部由编排脚本维护；worker 只报 status、失败签名和报告引用，传引用不传值。
8. `communication_mode` 只控制 worker 通信契约，不改变 task 上已声明的 `result_route`；两维组合不得互相覆盖。
