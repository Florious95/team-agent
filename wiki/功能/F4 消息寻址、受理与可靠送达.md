# F4：消息寻址、受理与可靠送达

## 一、用户获得什么

任何合法成员发出的消息都先形成一笔可追踪的交付义务，再送往唯一、正确的接收方。临时没有通道、目标重启或发生重试时，同一消息仍可继续交付，不会静默丢失、跨队误投或因恢复产生第二份副本。

用户可见承诺：

1. **收发双方唯一**：发送者、接收者和所属 team 必须由稳定身份确定；歧义时拒绝，不猜 sibling team 或“最像”的目标。
2. **先持久受理，后碰通道**：受理成功意味着已有稳定 `message_id` 和持久交付义务，不意味着已经送达。
3. **送达只认端到端证据**：排队、找到目标、执行注入或返回 ok 都不能冒充接收方对话已收到。
4. **恢复仍是同一消息**：通道恢复、pane 恢复或有界重试只重开原 obligation，保持内容、身份和去重标识，不创建第二条消息。
5. **状态不能倒退**：已经跨过物理提交边界的消息不能被普通 claim/attach 当作“尚未发送”重新开放。
6. **范围隔离**：leader 通道恢复只影响同 team、leader-bound、确实尚未物理提交的消息；worker、sibling team 和 terminal 消息不被连带冲刷。
7. **每个未送达都有解释**：当前卡在受理、通道、提交、收据还是停止预算，必须能从持久状态看出。
8. **发信只表达一比特呈现意图**：发送者只选择“上桌”或“投信箱”；不承担 message-class 分类。投信箱仍须持久落盘、可由 leader 回溯，并返回诚实的 durable-only 回执。
9. **send-now 队列检测增加门不替代门（在途，锚 `10137cda`，未发版）**：识别 grok/cursor 的 send-now 标记为四路平权取或，不是用新信号替换旧信号。规格全文：`.team/artifacts/grok-queue-mark-additive-gate.md`。每一路必须单独过零队列对照：该路单独启用时，无队列 pane 上按键次数必须为 0；合起来测通不算数。

## 二、怎样黑盒判真

### 唯一寻址与隔离

原文锚：

- `docs/team-agent-leader-passive-injection-goal.md` §2：`send_message(to="leader")` 不改变 task assignee/status
- 同文 §4.2：fake leader 收到的 payload 中 `from`、`to`、`task_id`、`message_id` 语义正确
- `docs/team-agent-skill-hardening-goal.md` §4「ACK/status 不得污染 task routing」

黑盒验收：

1. 同工作区建立两个 team，包含同名成员。
2. 指定 team 的消息只在目标接收侧出现；缺少唯一 team 时必须拒绝。
3. 普通 status/ACK 即使携带 task 引用，也不能把 task assignee 改成 leader。
4. 事件、持久行和接收侧证据中的 owner/sender/recipient/message_id 必须一致。

### 先持久化与诚实状态

原文锚：

- `docs/team-agent-foundation-and-boundaries.md` §14：区分 accepted、target_resolved、injected、visible、consumed、failed、ambiguous
- `docs/team-agent-quick-start-and-blackbox-goal.md` Phase 2、Phase 3：受理、目标解析、物理注入与可见证明分阶段
- 同文 §8：delivery token 与默认等待必须有自动测试

黑盒验收：

1. 在目标通道缺失时发送，发送端返回稳定 `message_id`；持久库存在同一行并说明阻塞原因。
2. 修复目标通道后，原 `message_id` 继续推进；不得新建内容相同的替代行。
3. 物理提交失败时不能标 delivered；只有与该 `message_id`、目标和 attempt 匹配的接收侧/对话流证据才能终结 obligation。
4. 重复提交同一个 `message_id` 不产生第二次业务投递。

### 恢复边界与风暴反面齿

原文锚：

- `docs/team-agent-foundation-and-boundaries.md` §14：`injected` 不能直接称为 delivered
- `docs/team-agent-quick-start-and-blackbox-goal.md` §9：worker 消息必须进入真实对话，不能靠 leader 轮询
- `wiki/contracts/信箱重放契约.md`「允许恢复的范围」「保持不变」
- `wiki/contracts/S3-物理注入到收据.md`「只有两种端到端结果」

黑盒验收：

1. 准备四组历史库存：尚未物理提交的 leader blocked、已经物理提交但待 receipt 的 parked、terminal、非 leader。
2. 显式恢复 leader 通道。
3. 只有第一组按白名单重开；parked、terminal、非 leader 均保持原状态。
4. 恢复前后逐状态统计总数、重开数与拒绝数；任何全库扫描、状态合并或数量不守恒都判失败。
5. 重开后的消息仍走原有受理→单赢家→物理提交→receipt 漏斗，不能从恢复路径直接注入。

### 并发与中途终止

原文锚：

- `docs/team-agent-skill-hardening-goal.md` §4「send 串行 guardrail」「collect 不得部分污染 state」
- 同文 §5 Fake/tmux E2E：send、result、collect 与 shutdown 必须形成完整链

黑盒验收：

1. 并发发送或并发恢复同一消息时，只有一个 attempt 获得提交资格。
2. 在恢复批次中途终止进程，重新启动后只能从持久行继续，不重复已完成部分。
3. 任何失败都不能留下“状态已重开但恢复 incident/attempt 未记”或“watcher 已推进但消息未推进”的半批次。

### 单信箱参数与 durable-only 回执

正式需求锚：`.team/artifacts/0.5.60-message-plane-requirements-20260725.md` §1「send 单信箱参数」、§2「class 体系」「policy 强制面」。

专项需求与锚号：[[send 单信箱与状态事实穿透]]。

设计依据：参数落在信息所在的地方。是否打断 leader 只有发送者在当刻知道，但判断只需“上桌/投信箱”一比特；要求发送者再选择全局 message-class，会把 policy 分类作业错误推给 agent。

黑盒验收：

1. send 侧只暴露一个“投信箱/上桌”的一比特选择，不要求发送者填写 message-class，也不开放第二套流程分类参数。
2. 选择投信箱后，消息形成稳定持久行和 `message_id`，leader 主屏不发生 live inject。
3. 发送端回执明确为 `stored_only`，验证事实为 `durable_without_live_inject`；只写日志、未持久化或仍发生 pane 注入均失败。
4. 选择上桌时仍走既有可靠送达链；一比特选择不能绕过身份、持久受理、单赢家、receipt 或恢复边界。
5. failed、fallback、blocked、timeout 等状态事实无条件上桌；stage_pass、final_review 等发送方自报标签不得覆盖事实 policy。
6. 信箱浏览标签从发件人、task_id、status 等既有事实派生，不要求发送方维护分类词表。

### send-now 四路或门（在途，锚 `10137cda`，未发版）

原文锚：用户裁定 2026-08-18；规格全文 `.team/artifacts/grok-queue-mark-additive-gate.md`。

四路平权取或，命中任一即队列态存在：

1. 页脚含 `Enter:send now`
2. 页脚含 `Enter to send now`
3. 某行以 `#<数字>` 开头且含 `Team Agent message from `
4. 某行以 `#<数字>` 开头且含 `(+<数字> lines)`

黑盒验收：

1. 在真实 grok 席位上分别造出第 1 路与第 2 路各一次，检测器在两种态都判真。只覆盖一种不算过。
2. 四路各自单独启用：无队列 pane 上按键次数必须为 0。合起来测通、未做单路零队列对照，本条失败。
3. 四路都不命中 ≠ 已提交，只等于没看见队列。
4. 命中后只重按回车，不重粘文本、不用 Escape。
