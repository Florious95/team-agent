# F8：状态观察、诊断与人工干预

## 一、用户获得什么

leader 能以短摘要看见团队、成员、消息、任务、会话和资源的当前事实；需要处理异常时再逐层展开证据，并通过通用“看 + 按”原语干预。观察失败、未知和业务失败必须分开。

用户可见承诺：

1. 权威状态、平台观察和推断分层，弱观察不能覆盖更强事实。
2. 每个拒绝、未执行和未知都有 reason、时间、来源与检查范围。
3. 默认摘要保护 leader attention；原始日志和 JSON 按需拉取。
4. 看/按是通用原语，不为每种 prompt 固化业务流程。
5. 人工干预有精确目标、权限检查、动作日志和结果边界。
6. 后台观察不调用真实 provider 消耗隐藏 token。
7. **一个字段不承载两种语义（在途，锚 `10137cda`，未发版）**：`status` 的 `ok` 只表示命令成功（类型不变，成功路径恒真）。grok 身份槽健康另用顶层布尔 `grok_identity_slot_ok`。一次成功的 status 调用不得再返回 `ok: false` 来表示身份不健康。

准则锚：基础边界 §13、§17、§18；skill-hardening goal §4「diagnose 增强」。

## 二、怎样黑盒判真

### 状态分层

原文锚：quick-start goal Phase 4、§8；restart goal §5 的 status session facts。

1. 构造 live、dead、probe-error、unknown 四种节点；输出不得把 error/unknown 当 dead 或 idle。
2. 状态列出 source、timestamp、checked paths；历史 event 不冒充当前态。
3. recent successful delivery 等强事实不能被一次 shell/pane 快照覆盖。

### status 命令成功与 grok 身份槽健康分键（在途，锚 `10137cda`，未发版）

原文锚：用户裁定 2026-08-18。可抽象承诺：观察面的“命令成不成功”与“被观察对象健不健康”必须分开。

1. 命令成功且 grok 身份槽健康：`ok` 为真，`grok_identity_slot_ok` 为真。
2. 命令成功但 grok 身份槽不健康：`ok` 仍为真，`grok_identity_slot_ok` 为假。消费者必须能区分这两种成功。
3. 命令本身失败：`ok` 为假；不得用 `ok` 同时表达命令失败与身份不健康。
4. `ok` 类型与成功路径恒真的既有语义保持；不得改成枚举或三态来塞进领域健康。

### 诊断可操作

原文锚：skill-hardening goal §4「diagnose 增强」与 §5 approval blocker 替代验收。

1. approval、interrupted、leader channel 缺失、session miss 各返回不同原因。
2. 每项给可执行下一步与证据位置，不要求读源码或手改 state。
3. 修复后诊断当前态更新，旧事件保留历史时间标识。

### 看与按

原文锚：基础边界 §17；设计备忘录二.4、三.6。

1. leader 读取目标成员最近输出与结构化状态。
2. 对需要人工确认的 prompt，动作前显示目标、输入和权限；动作后记录 executed/failed/fire-and-forget。
3. sibling pane、别 team 或权限不足时拒绝，不能猜目标。
