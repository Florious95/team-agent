# F2：角色、成员与能力编排

## 一、用户获得什么

用户用自然语言角色文档说明“谁负责什么、使用什么能力”，leader 据此组队并在运行中增删、重启、重置、克隆或分叉成员。角色定义是可读的一等资产，运行产物不能反向成为用户必须维护的第二套真相。

用户可见承诺：

1. **角色文档即入口**：成员职责、边界和能力以自然语言为主；机器字段只承载最少运行元数据。
2. **leader 自由编排**：系统提供成员与能力原语，不预定义固定角色集合、工作流图或审批模板。
3. **成员存在性一致**：添加成功后立即可寻址；移除后不再属于 roster；失败不得留下 spec、状态或健康记录的半成员。
4. **角色身份不漂移**：重启、恢复、克隆或分叉不会悄悄改变 persona、provider 或权限边界。
5. **两种复制语义可区分**：克隆得到同一知识基底的全新成员；分叉得到独立且可验证的上下文分支。不能把“新进程已出现”伪装成“上下文已分叉”。
6. **通信契约可选且不漂移**：用户可在 team 级选择官方通信模式，并在 role 级覆盖；未声明时保持 `leader_centric`。成员经 fresh、fork、restart/resume 或 start-agent reconstruction 后，有效模式不变，且不改变身份、权限和结果义务。
7. **Pi 角色沿用共享字段并可省略 model/effort（用户会签 2026-08-31）**：已由其他 Provider 建立的团队可以添加 Pi TeamMate。Pi TeamMate 角色允许省略 model 和 effort。Pi 沿用 Team Agent 已有的共享角色字段及权限语义，包括 MCP、tools 和 `dangerously_skip_permissions`；不为 Pi 发明第二套字段、别名或 `auto`/`skip` 等不同表达。reset 丢弃旧会话并建立 fresh 会话，且不得影响 sibling 席位。Pi 专属 Provider 行为见 [[F3 Provider、模型、权限与资源组合]]；会话边界见 [[F7 会话身份、续作、克隆与分叉]]；条款地图 [[Pi provider 适配]]。

明确非目标：

- 不提供固定角色模板市场。
- 不让用户维护复杂 role DSL、DAG 或 state machine。
- 不允许运行时 pane、进程名或一次观察反写角色本体。
- 不把编排层的每个目录或工作习惯做成框架命令。
- 不为 Pi 发明第二套字段、别名或 `auto`/`skip` 等不同表达。
- 强制用户填写 Pi 角色的 model 或 effort。

## 二、怎样黑盒判真

### 文档驱动组队

原文锚：

- `docs/team-agent-codex-foundation-rust-goal.md` §1「任务宣言」：`用户可读团队/角色文档是入口；runtime manifest 是编译产物`
- 同文 §8「自动测试要求」：role docs compile
- 同文 §12「完成标准」第 2 条：role docs compile 可用，旧 spec 入口不破坏
- `docs/team-agent-restart-foundation-goal.md` §9.3：不带 agent 字段的 TEAM.md + 一份 worker role doc，quick-start 成功且状态无 `leader` 行

黑盒验收：

1. 只提供团队文档与 N 份角色文档，启动后恰有 N 个 worker，不复制 leader。
2. 用户不编辑运行时 manifest 也能完成启动。
3. 修改角色文档后，通过明确的新一轮成员生命周期动作生效；旧投影不能覆盖新角色事实。

### 运行中成员管理

原文锚：

- `docs/team-agent-quick-start-and-blackbox-goal.md` §8、§12：角色文档进入运行配置，quick-start 从零到 ready
- `docs/team-agent-skill-hardening-goal.md` §4「collect 不得部分污染 state」：失败不能先改状态再崩溃
- 各 goal 完成标准：任一条件未满足必须标 partial/blocked 并给证据

黑盒验收：

1. 对 live team 添加成员，成功返回时该成员立刻能收消息、发消息并报告结果。
2. 移除成员后，同名寻址不再命中；重新添加时不会被旧残留错误阻塞。
3. 重启或重置只作用于目标成员，sibling 成员不掉线、不换身份。
4. 任一步失败后，角色文档、成员列表和可寻址集合保持一致，不出现“看似存在但不能用”的僵尸席位。

### 克隆与分叉

原文锚：

- `docs/team-agent-foundation-and-boundaries.md` §7：agent identity 与 pane/terminal transport 解耦
- 同文 §15：runtime 提供 session、handoff 和恢复事实，leader决定恢复或新开
- `docs/team-agent-restart-foundation-goal.md` §9：恢复后必须能引用前序对话内容，不能只证明进程启动

黑盒验收：

1. 克隆成功后，新成员有独立身份；未声称继承上下文时，不伪造 session/backing 证明。
2. 分叉成功后，必须存在与源成员不同、可核验且承接源上下文的新会话；源会话保持不变。
3. 若 provider 的新 backing 尚未形成，只能报告 pending；若无法证明上下文承接，只能拒绝，不能降级成普通克隆并报成功。
4. 同一源连续产生多个新成员时，每个新成员身份、会话和后续消息互不串位。

### Team 默认与角色覆盖

跨页验收锚：[[communication_mode 黑盒验收矩阵]]

黑盒验收：

1. team 与 role 均未声明时，所有成员获得 `leader_centric`。
2. team 声明一种模式时，无覆盖角色全部继承该模式。
3. 某 role 声明另一模式时，仅该角色使用覆盖值，siblings 保持 team 默认。
4. 未知枚举在成员生成前明确失败，不得静默回退、部分生成或保留半成员。
5. 同一角色经四类生命周期入口后，有效模式相同；fork 产生新身份但不丢失继承的有效通信模式。
6. 模式选择不得改变 provider、模型、identity、权限或角色正文。

### Pi 角色字段与 reset（用户会签 2026-08-31）

原文锚：`.team/artifacts/pi-provider-adaptation/requirements/pi-provider-requirement-final.md`。条款地图 [[Pi provider 适配]]。

1. 已由其他 Provider 建立的团队可以添加 Pi TeamMate。
2. Pi TeamMate 角色允许省略 model 和 effort。
3. Pi 沿用已有共享角色字段及权限语义，包括 MCP、tools 和 `dangerously_skip_permissions`；不为 Pi 发明第二套字段、别名或 `auto`/`skip` 等不同表达。
4. reset 丢弃旧会话并建立 fresh 会话，且不得影响 sibling 席位。
